# Prediction异常帧perf与CPU stack提取结论

## 覆盖与验证

- 输入：执行耗时严格大于全程P99的12帧：91、411、513、514、560、586、715、718、772、906、988、989
- 12帧全部完成TID身份映射、sched状态分解和逐帧上下文提取
- trace→sched同TID marker复核支持率：100%
- stack→sched同TID/同CPU复核支持率：96.4463%，通过95%门槛
- 原始数据：`perf.data` 8,577,502,162 bytes；`perf_sched_script.txt` 11,656,128,084 bytes；CPU stack原始data 13,192,540 bytes
- TID身份只有采集前快照，缺少after快照；结果保留这一证据限制

## 调度状态结果

12帧callback的CPU-resident时间都集中在2.680–3.495 ms，明显小于15.635–19.007 ms的callback墙钟耗时。异常延长主要表现为等待：

- runnable waiting主导：帧91为15.264 ms，帧411为14.102 ms，帧772为9.287 ms
- blocked主导：帧513、514、586、715、718、988、989，blocked约11.548–13.916 ms
- 混合等待：帧560为blocked 8.577 ms + runnable 4.343 ms；帧906为blocked 7.782 ms + runnable 5.133 ms

因此，这12帧不是统一由Prediction callback自身持续占用CPU计算过长导致。帧91、411、772更符合调度就绪等待；其余多数帧更符合阻塞/等待异步工作完成。`running`只表示CPU-resident，不能单独等同于有效计算。

## CPU stack结果

- 11/12帧命中CPU stack样本，共16个；帧91没有命中
- callback TID样本仅3个，分别位于帧715、718、906
- 其余样本多数落在异步SemanticMap绘制阶段，常见节点为`semantic_draw_lanes`，叶子符号包括OpenCV的`cv::Circle`、`cv::line`、`cv::FillConvexPoly`、`cv::ThickLine`等
- 99 Hz采样面对约16 ms窗口，每帧样本天然很少；这些样本可作为现场证据，不能据此计算精确CPU耗时比例或断言唯一根因

## 文件说明

- `frame_summary.csv`：12帧callback running/blocked/runnable及stack样本数
- `clock_calibration.json`：最终校准与二次支持率复核
- `tid_mapping.csv`：Container/Host TID映射证据
- 每个`Fxxxx`目录：该帧原始信息、节点实例、全部frame TID与callback TID的sched上下文、CPU stack原文及逐sample CSV
